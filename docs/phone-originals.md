# Полные файлы из каталога iPhone

Состояние на 1 октября 2026 года. Источник каталога и превью — сам iPhone. Вход в iCloud, чтение медиатеки Mac и установка приложения на телефон не выполнялись.

## Что уже подтверждено

Каталог содержит основную видимую категорию с 2 138 фото и 429 видео. Из нового снимка каталога, привязанного к USB-устройству, цепочка интерфейса получила и декодировала 12 превью фотографий и одно превью видео. Превью не доказывает наличия полного исходного файла.

В локальном снимке `ZINTERNALRESOURCE` содержит 10 932 строки, связанные с 2 807 строками ассетов, включая состояния удаления. На один ассет приходится несколько ресурсов. В схеме есть тип ресурса, локальная и удалённая доступность, длина данных; `ZADDITIONALASSETATTRIBUTES` также хранит заявленный исходный размер. Частные числовые значения пока не сопоставлены с оригиналами, Live Photo и правками. Наличие `ZCLOUDMASTER` не означает, что байты оригинала находятся на телефоне.

Поэтому нельзя считать один файл с совпавшим именем полным архивом ассета и подключать к нему удаление с телефона.

## Загрузка оригинала только в iCloud

В опубликованном API libimobiledevice 1.4.0 AFC предоставляет файловые операции; отдельной операции запроса оригинала из iCloud не найдено. Открытие `AFC_FOPEN_RDONLY` не документировано как команда загрузки облачного файла. Это ограничение проверенного API, а не доказательство отсутствия всех частных протоколов. Источники: [API AFC](https://github.com/libimobiledevice/libimobiledevice/blob/1.4.0/include/libimobiledevice/afc.h), [реализация](https://github.com/libimobiledevice/libimobiledevice/blob/1.4.0/src/afc.c), [операции протокола](https://github.com/libimobiledevice/libimobiledevice/blob/1.4.0/src/afc.h).

Документированный механизм есть в PhotoKit: приложение разрешает сеть через `PHAssetResourceRequestOptions.isNetworkAccessAllowed`, и отсутствующие данные загружаются из iCloud. API не описывает удалённый USB-вызов библиотеки подключённого телефона. В нашем сценарии это был бы отдельный компонент на iPhone, который пока не установлен и не выбран пользователем. [Документация Apple](https://developer.apple.com/documentation/photos/phassetresourcerequestoptions/isnetworkaccessallowed).

Руководство iMazing от 13 мая 2026 года описывает каталог и миниатюры с устройства, а для экспорта cloud-only объектов требует входа в iCloud и загрузки с серверов Apple. Это подтверждает другой путь, но не доказывает возможность запросить загрузку оригинала самим телефоном через AFC. [Руководство iMazing](https://imazing.com/guides/how-to-manage-and-transfer-photos-between-iphone-ipad-and-computer).

## Ограниченная проверка пути

Подготовлены `asset-header.c` и `run-asset-header-probe.py`: чтение атрибутов и не более 16 байт одного файла по `ZDIRECTORY/ZFILENAME` из проверенного снимка. Привязка USB-устройства проверяется до открытия сессии. Этот опыт проверяет доступность конкретного пути и сигнатуру формата; он не переносит файл и не устанавливает его роль в полном архиве. Helper прошёл строгую C-сборку и отдельный review; все семь Python fixture-тестов AFC проходят.

```sh
python3 experiments/afc/run-asset-header-probe.py --snapshot '/путь/из/snapshotPath' --asset-id 123
```

Первый запуск для новых/старых фото и видео остановился на обнаружении устройства: USB 0, сеть 1. Проверка `ioreg` и usbmuxd подтвердила отсутствие USB-подключения. Файлы телефона не читались; делать вывод о доступности оригиналов по этому результату нельзя. Проба по сети не выполнялась. Для продолжения нужен подключённый и разблокированный iPhone.

Если путь отсутствует, отдельно проверить его после загрузки выбранного объекта средствами самого iPhone и обновления каталога. Результат такого опыта не означает, что Mac умеет автоматически управлять загрузкой из iCloud.

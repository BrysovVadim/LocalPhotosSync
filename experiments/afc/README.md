# Проверка каталога самого iPhone без установки

Эксперимент использует обычный `com.apple.afc` через существующую доверенную USB-пару. Проба каталога читает `/PhotoData/Photos.sqlite` и при копировании — доступный `/PhotoData/Photos.sqlite-wal`. Отдельная проба миниатюры читает ограниченный файл кэша из `PhotoData/Thumbnails/V2`. Приложение на iPhone не устанавливается; медиатека Mac не используется. Это частная схема базы iOS, а не гарантированный контракт Apple.

## Подготовка на Mac

Нужны Xcode/clang, Homebrew и Python 3.12+ для безопасной распаковки. Homebrew только скачивает и проверяет bottles в рабочую папку; глобальной установки нет:

```sh
HOMEBREW_NO_AUTO_UPDATE=1 HOMEBREW_CACHE="$PWD/.build/afc-homebrew-cache" brew fetch --deps --force-bottle libimobiledevice
python3.12 experiments/afc/prepare-runtime.py
```

Проверены libimobiledevice 1.4.0, libusbmuxd 2.1.1 и libplist 2.7.0, bottles arm64_tahoe. Пути заголовков в runner соответствуют этим версиям. При изменении версий нужно проверить сборку; существующие файлы распаковщик не перезаписывает. В текущей рабочей папке runtime уже подготовлен.

## Проба

```sh
python3 experiments/afc/run-probe.py
python3 experiments/afc/run-probe.py --copy-metadata
python3.12 experiments/afc/inspect-catalog.py '/путь/из/snapshotPath'
```

Первая команда читает размер и 16 байт заголовка с общим дедлайном процесса 20 секунд. Вторая создаёт новую приватную папку в `.build/phone-catalog-probe/`, копирует метаданные с дедлайном 90 секунд. Лимиты: база 256 МиБ, WAL 64 МиБ. Данные сохраняются потоково, файлы создаются с правами `0600` без перезаписи. Частичные результаты сохраняются при ошибке; их нельзя считать пригодным каталогом. `.build` исключена из Git.

Только успешное копирование создаёт `catalog-receipt.json` с правами `0600`. Вкладка приложения требует этот отчёт, сигнатуру SQLite и совпадение размеров базы/WAL. Начальная загрузка и обновление выполняются последовательно; ошибка обновления сохраняет прежний пригодный каталог. Согласованность исходного снимка остаётся недоказанной даже при корректном отчёте.

Автоматического создания пары нет. HostID извлекается из существующей записи только в памяти; сертификаты и ключи использует библиотека. Диагностика не содержит имён фотографий, идентификаторов устройства или записи пары. При отсутствии пары, отказе, блокировке или неподдерживаемом TLS операция заканчивается с ошибкой. Удалённых операций записи и удаления нет.

## Результат на подключённом телефоне

30 сентября 2026 года: получены база 117 596 160 байт и WAL 5 500 232 байта. Наблюдаемые размер/время изменения каждого файла совпали до и после его копирования. SQLite `quick_check` вернул `ok`. Это **не** доказательство атомарного снимка базы и WAL.

В `ZASSET` 2 807 строк, включая 121 строку с состоянием удаления. Не удалено: 2 245 фото и 441 видео. Видимые записи основной категории `scope=0`: **2 138 фото и 429 видео**. Дополнительная категория `scope=3/type=12` содержит 105 фото и 12 видео; исследование iOS 17 связывает её с Shared with You. Ещё две фотографии имеют признаки невидимых элементов серии. Эти интерпретации требуют проверки при изменении iOS.

Видео совпали с прежним числом пользователя, по фото осталось шесть дополнительных записей. Причина пока не установлена. Число строк базы не равнозначно числу файлов, области PhotoKit или доступным оригиналам. Облачные оригиналы и удаление этим экспериментом не проверены.

## Миниатюры

1 октября 2026 года одна миниатюра получена с телефона: JPEG, 55 481 байт, 360×780. Изображение полностью декодировано через ImageIO. Оригинал при этой проверке не читался. Это доказательство одного доступного превью, а не покрытия всей медиатеки.

Затем новый снимок каталога с привязкой к устройству прошёл ту же цепочку загрузки и декодирования, которую использует интерфейс: **12 из 12 выбранных фотографий и 1 из 1 видео** получили превью, ошибок и недоступных превью в этой выборке не было. Отрицательная проверка с изменённым digest привязки завершилась `source_binding_mismatch`: 0 обращений к путям миниатюр и 0 прочитанных байт. Полное покрытие библиотеки по-прежнему не подтверждено.

```sh
python3 experiments/afc/run-thumbnail-probe.py --snapshot '/путь/из/snapshotPath'
python3 experiments/afc/run-thumbnail-probe.py --snapshot '/путь/из/snapshotPath' --asset-id 123
python3 -m unittest discover -s Tests/AFCThumbnail
```

Нужен новый снимок каталога с `source-binding.bin`: старые снимки без привязки не допускаются к чтению превью. Этот приватный файл содержит версию, случайную соль и SHA-256 соли вместе с идентификатором выбранного USB-устройства. Сам идентификатор и ключи пары не записываются. Перед открытием сессии миниатюры проверяется совпадение телефона; идентификаторы и digest не выводятся в JSON.

По умолчанию выбирается одна активная, видимая, нескрытая фотография основной категории. `--asset-id` допускает фотографию или видео; это локальный ключ записи снимка каталога, значение связывается с SQL-параметром. Имя и каталог передаются helper через stdin. Допустимы только фиксированные пути `V2/<ZDIRECTORY>/<ZFILENAME>/5005.JPG` и `5003.JPG`; переход ко второму выполняется лишь при отсутствии первого. Максимум 4 МиБ, компиляция до 10 секунд, процесс чтения до 30 секунд. Каждый helper компилируется в отдельной приватной UUID-папке `.build/probe-executables/`, чтобы несколько экземпляров приложения не перезаписывали работающий файл. Артефакты сохраняются. Частичные изображения остаются в приватной `.build/phone-thumbnail-probe/` и не считаются успешным превью.

В интерфейсе серия ограничена 12 превью и общим монотонным дедлайном 45 секунд. Завершаются и runner, и его дочерний helper. Кэш в памяти ограничен 96 изображениями; скрытые и дополнительные категории в этой итерации не получают превью.

Отдельная [проба полного файла](../../docs/phone-originals.md) читает лишь атрибуты и максимум 16 байт пути ассета. Она не используется интерфейсом, не создаёт копию медиа и не подтверждает полноту оригинала. На первом запуске USB уже отсутствовал, поэтому доступность файлов ещё не проверена.

Пути основаны на [наблюдениях устройства с iOS 16](https://forensicfolder.wordpress.com/2025/09/12/ios-photos-application-forensic-overview/) и [эксперименте с оптимизацией хранения](https://theforensicscooter.com/2022/12/05/do-you-have-a-full-sized-assetor-just-a-thumbnail-did-optimized-iphone-storage-process-occur/). Это не контракт для всех версий iOS. Привязка проверяет телефон, но не неизменность пути после снимка каталога.

Источники: [стандартный AFC/ifuse](https://github.com/libimobiledevice/ifuse#usage), [API AFC](https://github.com/libimobiledevice/libimobiledevice/blob/1.4.0/include/libimobiledevice/afc.h), [исследовательский запрос iOS 17](https://github.com/ScottKjr3347/PhotoData-Synd-Photos.sqlite_Queries/blob/main/iOS17_PhotoData-SyndPL_Photos.sqlite_Queries/1.9.17_iOS17_PhDaPs-or-SyndPs_Assets_REFERENCE.txt).

## Ограниченное копирование доступного файла

```sh
python3 experiments/afc/run-asset-copy-probe.py --snapshot '/путь/из/snapshotPath' --asset-id 123
python3 -m unittest discover -s Tests/AFCAssetCopy -v
```

Один доступный основной файл до 32 МиБ, поток 64 КиБ, дедлайн helper 60 секунд. Источник — только тот USB-iPhone, к которому привязан снимок; автоматической пары, записи и удаления на телефоне нет. Новая приватная папка содержит `media.bin` и отчёты с правами `0600`, без перезаписи. SHA-256 потока рассчитана на Mac; вызывающий код должен независимо перечитать сохранённый файл и сравнить digest. `stableObserved=false` нельзя считать стабильным результатом.

На реальном телефоне PNG 219 786 байт и видео 17 889 288 байт скопированы и независимо проверены. Проверка доступного файла не подтверждает полноту оригинала или Live Photo. Временные результаты — в `.build/phone-asset-copy-probe/`.

## Проверка скопированной пары Live Photo

Standalone verifier читает два локальных файла и их private copy receipts. Он проверяет размер и SHA-256 каждого файла, декодирование изображения, content identifiers, видеоконтейнер и загрузку пары через `PHLivePhoto` с явными file URLs. Медиатека Mac не используется, данных телефона verifier не читает и не меняет. Это проверка одной пары, не разрешение на удаление.

```sh
swiftc -swift-version 5 Sources/LocalPhotosSyncUSB/ArchiveReceipt.swift experiments/afc/verify-live-photo.swift -framework AppKit -framework AVFoundation -framework ImageIO -framework Photos -o .build/verify-phone-live-photo
```

На входе — приватный JSON с правами `0600` и полями `imageFile`, `movieFile`, `imageFolder`, `movieFolder`, `proofFolder`. Изображение и MOV до 32 МиБ с правами `0600`, директории приватные, внутри каждой source-папки — `copy-receipt.json` от helper. Реальные fixture inputs и медиа остаются в `.build` и не входят в Git.

Для всего процесса нужен внешний таймаут: встроенные десять секунд ограничивают callback `PHLivePhoto`, а не все операции AVFoundation и файловой системы. Пример для существующего приватного fixture:

```sh
python3 - <<'PY'
import subprocess, sys
try:
    result = subprocess.run(['.build/verify-phone-live-photo', '.build/latest-live-photo-proof-inputs.json'], capture_output=True, text=True, timeout=30)
except subprocess.TimeoutExpired:
    print('{"verified":false,"status":"verifier_timeout"}')
    sys.exit(1)
print(result.stdout.strip())
sys.exit(result.returncode)
PY
```

Выход — только агрегаты; `verified=true` и код 0 означают проверенную пару, отказ — код 1. Реальная связанная пара прошла проверку. Отрицательный fixture с читаемым обычным видео получил `movie_identifier_missing`: видео проигрываемо и хеши совпадают, но идентификатора пары в нём нет.


## Ограниченное сохранение одной Live Photo

Команда выбирает один неотредактированный видимый снимок основной категории из проверенного снимка каталога, сохраняет изображение и предполагаемый соседний MOV, затем запускает локальный verifier выше. На iPhone ничего не устанавливается; оба файла читаются только через AFC_RDONLY с проверкой привязки устройства до сессии.

```sh
python3 experiments/afc/run-live-photo-copy-probe.py --snapshot <verified-snapshot-folder>
```

Для конкретного ассета можно добавить `--asset-id <positive-int64>`. Без него берётся первый подходящий кандидат по убыванию внутреннего ключа базы; это не обещание выбрать самый новый снимок. Отбор по приватным полям базы — экспериментальная гипотеза, а не контракт Apple. `ZVERSION` не интерпретируется: несколько ресурсов одной роли отклоняются независимо от их версий. Путь MOV предполагается по общему имени; совпадение пары подтверждается только независимой проверкой встроенных идентификаторов и `PHLivePhoto`.

Лимит — 32 МиБ на каждый файл; два чтения идут последовательно, до 60 секунд каждое. Сборка C ограничена 10 секундами, сборка verifier и его выполнение — по 30 секунд. Частичные данные остаются в приватных папках `.build`; имена файлов и идентификаторы не выводятся. `complete.json` создаётся только после успешного кода возврата verifier и всех проверок. Этот маркер подтверждает проверенную пару файлов, а не полноту оригинала, данных правок или безопасность удаления.

11 fixture-тестов проходят. Полная цепочка новой команды прошла на ранее полученной с iPhone паре: 6 846 430 байт, повторные хеши, декодирование и загрузка `PHLivePhoto`. Это локальная проверка с подстановкой уже сохранённых копий вместо нового чтения устройства. После повторного подключения iPhone эта же команда аппаратно сохранила выбранную связанную пару: один снимок и один MOV, 6 846 430 байт, `verified=true`, код 0. Создан маркер проверенной пары; оба файла получены новым чтением AFC. В версии 0.4.0 отдельная кнопка «Сохранить Live Photo…» вызывает эту цепочку, переносит оба файла в выбранную папку и проверяет итоговый архив. Реальный backend-прогон прошёл; ручной выбор карточки пользователем ещё предстоит проверить.

```sh
python3 -m unittest discover -s Tests/AFCLivePhoto -p 'test_*.py' -v
```
